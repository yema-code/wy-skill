# 工作流与阶段

本文件规定多步骤项目的输入、阶段输出和停止条件。用户可以从任意阶段开始；缺少前置数据时只补齐必要部分。

## 项目预检

开始时确认或明确采用默认值：

- 产品：具体英文名称、同义词、型号/规格和应用；图片只能补充，不能替代产品词。
- 市场：国家/地区，必要时到城市；本地语言关键词应说明语言。
- 区域覆盖：用户要求多个大区时，每个大区单独做市场优先级、产品本地化和客户覆盖，不用一个国家代表整个大区。
- ICP：进口商、分销商、承包商、项目开发商、品牌商、零售商或其他类型。
- 排除项：消费者、电商聚合页、竞争者、无官网公司、不服务目标地区等。
- 批量：默认最多交付 10 家合格公司，不承诺凑满。
- 保存：多公司任务默认本地 SQLite；Notion 和文件输出按需启用。

不同类别的产品拆成独立项目。同一类别的相关产品可以共享项目，但评分时分别记录匹配证据。

## 阶段 1：产品与搜索准备

输出：

1. 一句话产品定位、典型应用和关键卖点假设。
2. ICP 与排除画像。
3. 关键词矩阵：核心词、同义词、应用词、买家角色词、采购/渠道意图词、竞品/替代词、负向词，以及英语和目标市场常用语言。
4. 按 [discovery-playbook.md](discovery-playbook.md) 设计搜索查询族和优先级，不只给一串同义词。
5. 可选的快速市场扫描或标准调研。
6. HS 编码候选、依据和不确定性。用户确认前不得据此得出海关数据结论。
7. 各市场的套件定义、尺寸、材质、合规、渠道和价格带差异；无法确认的产品参数列为供应商待确认。

## 阶段 2：搜索潜在客户

先查本地 CRM，按官网域名去重，再做实时搜索。查询应覆盖至少三类来源，例如公司官网、行业名录/展会、专业网络、协会/注册信息、可信新闻或项目资料。

先做官网、地理、业务匹配、硬排除和域名去重的快速预筛。每家公司再进入候选池，按评分规则进入：

- `qualified`：达到阈值且无硬排除项。
- `review`：证据不足、身份关系不清或分数接近阈值。
- `rejected`：不匹配或命中排除项，并记录原因。

停止条件：达到用户批量目标；或完成至少 5 个实质不同的查询族、覆盖至少 3 类来源，且连续 2 个查询族没有新增合格公司。遇到访问限制也停止该来源。报告真实产量、覆盖范围和短缺原因。

用户选择 TikTok B2B 获客时，不用搜索阶段替代内容获客；读取 [tiktok-acquisition.md](tiktok-acquisition.md)，先完成市场/账号定位与内容准备，再把公开询盘按企业身份和采购意图筛选后写入同一 CRM。消费者咨询和无法识别公司的账号不直接变成合格客户。

## 阶段 3：关键联系人

只为已确认公司寻找公开职业身份。按 [contact-routing.md](contact-routing.md) 根据公司规模、销售模式和采购场景建立决策链，优先采购、项目、技术、产品、合规、业务发展、创始人或管理层，不默认 CEO 第一。

最多排序三位联系人。每位包含姓名、完整职位、角色排名、排序理由、来源、观察日期和未知项。只找到一位时只交付一位。

## 阶段 4：公开工作联系方式

先找公司官网或本人职业资料明确公开的工作联系方式，再找可信专业来源。分别记录邮箱、工作电话/WhatsApp、公司 LinkedIn、Facebook、Instagram 和 TikTok；未找到要显式标记。

邮箱和电话状态必须遵循 [research-quality.md](research-quality.md) 的枚举。格式推测不等于可投递，通用邮箱不能冒充具体联系人邮箱。

## 阶段 5：客户背调

优先检查官网首页、About、Products/Services、Markets、Projects/Case Studies、News/Blog、Team、Contact 和法律信息，再补充外部来源。

每家公司输出：

- 公司身份、所在地、业务模式和覆盖市场。
- 与产品匹配的明确证据。
- 渠道、项目、客户类型和近期活动。
- 可验证的机会信号及其替代解释。
- 风险、冲突证据和未知项。
- 建议联系人、切入点与下一项最小验证动作。

同时检查与采购有关但不能单独证明采购意向的信号：新品/系列更新、促销、缺货、补货、展会、供应商页、门店扩张、招聘和企业社媒内容。保存替代解释，避免把营销活动直接写成采购计划。

## 阶段 5A：竞品、需求与社媒

用户要求竞品、需求、本地化或社媒时，读取 [competitor-social.md](competitor-social.md)。竞品与潜客分开建档，提取代表性产品的套件定义、材质、尺寸、价格、认证、包装、设计和渠道信号，再转换为供应商准备清单。

从官网发现并核验企业社媒。账号归属、活动状态和内容主题分别记录；只看到官网链接时活动状态必须是 `not_checked`。社媒用于研究与个性化，不自动关注、互动或私信。

完整性由字段和证据决定，不用固定 800 字制造冗长结论。

## 阶段 6：策略与草稿

只使用已核验证据和用户提供的产品事实。先选择首触达、沉默客户唤醒、报价或售后增购模式，再按公司规模、联系人角色和渠道生成草稿、异议处理和下一步目标。遵循 [outreach.md](outreach.md)，并把计划保存到 CRM。

## 阶段 7：Notion CRM

先读取 [integrations.md](integrations.md)。本地数据库是稳定源；用户明确批准并且连接可用时才创建、更新或同步外部 CRM。同步前预览新增、更新、冲突和跳过数量。

## 阶段 8：备用搜索

先读取 [integrations.md](integrations.md)。只有环境中确实存在可用提供方并且用户选择切换时才使用。无论搜索提供方是什么，都必须保存最终原始页面 URL，不能只保存搜索 API 摘要。

## 恢复与进度

多步骤项目用 `.wy/wy.db` 保存。恢复时运行：

```bash
python3 scripts/wy_crm.py status --db .wy/wy.db
python3 scripts/wy_crm.py validate --db .wy/wy.db
```

先总结当前阶段、记录数量、校验问题和推荐下一步，再继续。用户说“确认”时，只推进推荐的研究阶段；涉及外部写入或真实外联时另行取得明确授权。
